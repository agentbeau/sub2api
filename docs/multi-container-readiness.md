# Multi-container readiness gate

## Current runtime

- The public Worker and Access-authenticated browser route both dispatch to the stable Durable Object name `cf-singleton-container`. `wrangler.jsonc` keeps `max_instances: 1`.
- CPA v8.0.67 selects provider credentials and performs OAuth/token refresh internally. Its session-affinity selector and refresh mutex/cache are process-local. CPA config and credential records are persisted through the R2 S3 bridge; local container disk is not durable across sleep/restart.
- OAuth start binds the opaque state to its originating Durable Object, and callback ingress resolves that owner. This routes a callback to the same object but does not make CPA's in-memory PKCE verifier or provider session transferable across a container restart.
- Background activity callbacks carry the calling Durable Object ID as WorkerEntrypoint RPC props. Refresh work acquires a credential-specific lease with an epoch and renews it while running. Missing or malformed owner information fails closed.
- With `POOL_FENCING_ENABLED=true`, the pinned CPA Go object store acquires a per-object Worker lease and uses R2 conditional `PUT` with the ETag loaded at bootstrap or returned by its prior write. Config and auth writes reject unknown bases and conflicts. Fenced deletes write a conditional zero-byte tombstone because R2 does not expose conditional `DeleteObject`; empty auth objects are skipped by CPA's loader. The R2 S3 bridge enforces the same lease at the write boundary. See [R2's atomic conditional-write API](https://developers.cloudflare.com/r2/api/s3/conditional-operations/) and [Workers API `onlyIf`](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

These hooks establish fencing for refresh execution and shared object writes when explicitly enabled. The pinned CPA patch now also restores explicit provider/model/session credential bindings from the existing coordinator DO after a cold process start. It stores a SHA-256 key, the stable owner DO ID, and the CPA credential ID only; it does not persist tokens, prompts, history, or tool data. Reads and writes require the owner DO ID that received the routed request, and each selected request advances a version so a late result cannot erase a newer in-flight binding. A competing credential choice fails before CPA submits the provider request, and result invalidation uses the version attached to that request. A failed/unknown bridge write is not retried. This does not restore PKCE verifiers, LCP-derived affinity, in-flight provider protocol state, or conversation/tool execution state. Changing the shard mapping requires an explicit affinity migration; a new owner fails closed on existing records. The live application therefore remains on one container with affinity and fencing off until the routing, storage-lifecycle, restart, and exact-pair acceptance gates below pass.

## Preparation in this branch

`src/pool-coordination.ts` contains atomic lease, fencing epoch, OAuth callback-owner, versioned session placement, explicit-session credential-affinity, and shared-state compare-and-swap support. When the opt-in `POOL_SESSION_ROUTING_ENABLED` flag is enabled, `src/session-routing.ts` maps an explicit request session ID to one of three fixed Durable Object names. The original `cf-singleton-container` identity is shard zero; two new names are versioned and stable. The owner comes only from explicit session headers or bounded protocol metadata, never prompt text or an API key. Requests without an explicit session—including `previous_response_id`-only Responses continuations—stay on the legacy singleton. The request body is cloned only for a bounded JSON inspection and the forwarded body remains intact. `POOL_SESSION_AFFINITY_ENABLED` is separately required and is passed to the container only when fencing and session routing are both enabled.

OAuth start and callback ingress remain on the singleton. The callback state is bound to the starting DO. On a confirmed cold container start, the DO removes only its own callback bindings before discarding its process-local lease record; the PKCE verifier is not copied to durable storage. An unavailable coordinator blocks a replacement start. An old callback after process loss therefore fails closed and the user must restart the login flow. Stable DO naming preserves the session's shard after restart. The durable affinity hook covers explicit session IDs with provider and model separation; LCP-derived bindings and process-local protocol state still do not survive a restart.

The feature flags are off. The existing deploy artifact guard rejects session-owner routing unless durable session affinity and fencing are also configured, and still rejects pool deployment until the reviewed ownership/restart gates pass; `max_instances` remains one. The durable affinity records currently have no background compaction, and the global coordinator’s request rate, storage growth, write amplification, and p95 latency have not been load-tested. Each explicit-session request now does a durable read and a conditional version write, which needs representative traffic measurement before enabling. Workerd tests exercise Worker-to-DO dispatch, bounded affinity RPCs, owner-ID enforcement, concurrent versioned claims, restart restore, stale rebind/delete rejection, and actual R2 conditions; they do not represent provider inference or three running containers. Unit and integration tests cover concurrent refresh exclusion, stale-owner rejection, callback affinity, restart takeover, write conflicts, old-owner resumption and unknown write outcomes. The CPA patch wraps synchronous and background refreshes in per-credential ownership and routes activity renewal through the owning DO. Its Go object-store patch uses key-specific fencing and conditional writes. This branch is still preparation and does not establish live pooled continuity.

The v8.0.67 Home dispatch path selects credentials through an external control
plane and bypasses CPA's local selector. The durable-affinity patch now returns
503 before Home dispatch when its runtime opt-in is set. Until Home exposes and
enforces the same owner/version contract, Home mode is outside this pool gate.

## Required integration before raising `max_instances`

1. Keep a single integrated Worker and use explicit, stable session identity for affinity; never route based on guessed provider, ingress API key, or call type alone.
2. Load-test the explicit session affinity coordinator path and implement/verify bounded cleanup before enabling routing. Exercise alias/fallback ownership across shards and restarts; only the stable primary explicit session key is currently durably written. It is never an authorization decision.
3. Keep OAuth callback ownership bound to the start owner and explicitly fail closed if that owner's CPA process lost its verifier/session state. Do not claim to resume an in-flight authorization code exchange from a new process.
4. Preserve the new fenced Go writes in CI and add end-to-end tests against the exact Worker/R2 bridge pair, including unknown outcomes. Go tests simulate a conditional S3 server; one commits then drops the response to prove the CPA client neither replays nor rebases. The edge runtime test separately exercises real workerd R2 conditions.
5. Drain active streams before changing owner, never retry after output or tool side effects have been delivered, and verify zero active work before shutdown. Keep conversation/tool execution state separate from provider session affinity.
6. Test the exact Worker/container pair cold and warm, with concurrent refresh, OAuth start/callback, restart takeover, write contention, streaming and cancellation. Exercise only supported provider routes; Nathan's Claude, Gemini and OSS models use Antigravity OAuth and are excluded from live tests here.

The container pool is not enabled by this PR. No billing, OAuth, or provider-account semantics are changed.

The prepared production deploy now rejects a container artifact unless the existing `Cpa` class has `max_instances: 1`, before image push or R2/Worker writes. The existing isolated-preview guard independently compares its complete container configuration to the one-instance allowlist. Tests cover a three-instance artifact failing before any external writes.
